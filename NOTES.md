# Work in progress notes

Here are some notes that i made while doing this assessment. Mostly to explain my progress and decisions.

# Timeline

1. First I wanted to lay the basic codebase structure. Create the web server, routes and services. A structure like any other DI project available. 
    * I created the controllers at `routes` dir
    * A detection service that concerns finding and listing all checkboxes
    * and a classifier service that takes these found checkboxes and determines wether they are checked or not.

2. Set up an initial detection service that it's using vanilla openCV. It turns the image into grayscale, binarizes it and then finds contours. Based on all contours, it would try to find squares:
    * check if contour has area of square (height*width)
    * check if contour has 4 corners
    * checks if contour has "checkbox size" (a small number that depends on the size of the page. Totally arbitrary but worked for that time)
    * make sure element is not rectangular (width must be roughly equal to height)

3. A classifier was needed, and at the very beginning, I believe it was good to set a baseline. So an excellent naive classifier for this is to assume all checkboxes are unchecked. Think about it: if there is a checkbox in a document, its at least a yes or no question (so a 50-50 guess); there are even more times when its more than just a yes or no question, and in there you usually choose only one, so if there are 5 options, its a 80% guess of hitting the mark. I used this classifier as the BASE CASE for any other classifier.

4. Having created the detection and classifier services, I set up the tests to get results faster. Time limit is a week, and this is needed more than anything. At first, I used the images on the assessment PDF, which I carefully labelled and with LabelStudio. They have 286 checkboxes which is a good enough metric for small tests. My naive classifier was actually pretty good: 68% (beats 50% at least). 

5. Having set up testing, I needed to optimize. First thing was setting up a real classifier. I first looked for a pretrained classifier online, and found this one: [wendys-llc/checkbox-classifier](https://huggingface.co/wendys-llc/checkbox-classifier). It seemingly was able to classify checkboxes, to an advertised 95% accuracy. Small note was that this was trained on web UI checkboxes, not documents. The result was that this classifier beat my base case classifier by a very slight margin (70% vs 68%). It also took waaay too long to process any image. It was a good learning moment.

6. As existing pretrained classifier didn't match this domain, I went on to make my own small one. For this I found the following dataset: [meghnagera15/checkbox-cropped-binary](https://huggingface.co/datasets/meghnagera15/checkbox-cropped-binary/tree/main), which already provided multiple labelled fixed-sized images of checkboxes. I took these images and made my own CNN classifier based on this. This classifier has ~100k parameters, and achieved 94,8% accuracy (94,5% F1) on the test split of the checkbox dataset and 99,8% accuracy on the images at `/test/data`.

> [!NOTE]
> When can a checkbox be considered as `is_checked`?
> In my experience, it really depends on the context and the rules of each form. Forms usually tell you to `cross` or `tick` checkboxes, and some times even `fill` them. In some scenarios, like standardized tests, when you crossed a wrong box and want to correct it, they tell you to fill the box and then cross or tick the right one. So the final `checked` answer depends more on the context. 
> As there are no rules at play here or no subclassification of wether a box is crossed, ticked, filled or just empty, this model assumes a box `is_checked` when the box is crossed, ticked or filled.

7. Having achieved a pretty good classifier, now the test results showed 99,8% F1 on classification and 85% F1 on detection. However most missed checkboxes were those that were checked, aslo there were wayy too many false positives: on the full res images, the detection mechanism found 395 possible candidates out of 288. So it was time to tackle a more hardened detection method. By taking a look at it, I noticed that while empty checkboxes are easily found, crossed checkboxes are much more difficult to properly identify, as the crosses they contain usually break the contouring heuristics I use to identify them. I've tried multiple approaches such as adjusting filters, and even trying to filter off diagonals and just keep straight lines to easily identify the box of the checkbox. The problem is that they throw off a lot of false positives.

8. I've found the following dataset ["roboflow.com/cogniquest-idc1w/checkboxes-xtv3p"](https://universe.roboflow.com/cogniquest-idc1w/checkboxes-xtv3p) which contains almost 3000 labelled scanned document images with checkboxes. I used this to train a YOLO26s object detection model. The training code can be found at `notebooks/yolo.ipynb` and the resulting model is at `models/checkbox_yolo.pt`. On the dataset's own test split it reached 92,8% F1 (93% precision, 92,7% recall). It took ~10h to train it using my AMD RX 6700XT at 100 epochs and batch size of 4. A risky investment of time, taking into account that at the beginning of undertaking this assigment I only had 48h available, and by the moment I decided on training it, I only had 24hs left. However after taking a look at the results, I was a little underwhelmed: F1 scores went from 85% to 91% on the test data. I took a look at it didn't take too long to find the root cause: when using high-res images, detection got worse!

9. Taking a look at why higher resolution images were failing against non-ML based approaches with openCV, I remembered that the model was trained for 1200px square images, but the high-res images went as far as 2200px, so it had to be a scaling problem. And it was: by default Ultralytics scales images with INTER_LINEAR which is great for upscaling but terrible for downscaling (our scenario here). So a simple check was made that if the image was greater than 1200px then just scale it down with INTER_AREA, which was much better at downscaling. This little trick bumped the F1 scores from 91% to 96% on the test data. Which now made the 10h time investment well worth it!

10. Having finished the backend, it was now time to show it off, as every project needs. So I set up a new frontend with react and vite. At first I made it simple enough to load a file via a file selector and then use simple square shapes to highlight the found checkboxes. I also took the opportunity to create a docker compose so anybody could deploy the whole project simply by doing `docker compose up`. Once that was out of the way, I took the small time left to try to optimize it a bit: I saw that only the first image took around 1s to load, and that was because the python program loaded all of the weights for the cnn and the yolo models on the very first run. I fixed it by adding an initial blank page inference at startup, which made startup slower but every user request now is fast. Finally, I added a fancier "drop" box where you could drag and drop your files into the box directly, and an error page; not because I experienced errors, but one can never be too careful with hosted programs on the cloud + virtualization. 

11. Having done all the hard part, now it was time for the easy part: hosting and publishing it. To host it I used a small VM on AWS (no GPU compute. I wanted the backend program to be fast enough to be able to run on CPU, and luckily its fast enough to do so!). The final link to the hosted version [can be found here](https://example.org).
